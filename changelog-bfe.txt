* Fix a crash in the download queue window, also in DC++ 0.884: an item that changed and was then removed while the window was opening (for example a file list that finished downloading at that moment) was updated after the window had already left it out, and DC++ closed. The window now starts listening to the queue in the same step as it reads it, so it no longer misses such changes or lists an item twice, and an update of an item it doesn't list is ignored (iceman50)
* Open the Experimental window, switch its tabs and resize it without flicker: the window, each tab and its lists now reach the screen in one finished picture, in light and dark themes, instead of drawing piece by piece with lists flashing black or empty. It also opens about a third faster and shows each tab for the first time about a quarter faster (iceman50)
* Return to the Experimental window from another tab at once: with several icon packages installed it took up to two seconds, because the icon preview was rebuilt once for every package in the list each time the window came back into view (iceman50)
* Unpack icon and emoticon packages once instead of every time they are read: each .dcico and .dcemo package is extracted, with the same size limits as before, into a folder of its own the first time it is used or after it changes (Extracted in %LOCALAPPDATA%\DC++, or beside DCPlusPlus.exe in the portable version), and read from there afterwards. Previewing an icon package takes about a tenth of the time, icons are no longer written to temporary files one by one, and the copies of packages that are removed or replaced are deleted. The packages themselves stay what you install, choose and share (iceman50)
* Move the theme editor, the icon and emoticon packages and every option DC++ Experimental adds to DC++ out of Settings into a window of their own, View > Experimental, with the tabs Themes, Icons, Emoticons, Chat and sharing, Transfers and hashing, Private Send, Protocol limits and Other (which has the password lock and the country database URL). Settings keeps the options of DC++ itself, and a page that opens the window. Each tab lays its options out in two columns across the window (one when it is narrow), with the help for the selected option below them. Changes apply at once instead of waiting for OK: check boxes and lists when changed, numbers and text after a short pause in typing, on Enter or when leaving the field, and theme edits a moment later; they are saved automatically. Icon packages are previewed in their own icons, on light and dark backgrounds, before they are used. The window opens in well under a second: each tab is built when it is first shown, or in the background while the window is idle (iceman50)
* New option "Largest file list to download" on the Transfers and hashing tab of the Experimental window (default 512 MiB, 0 = no limit): a full file list announced as larger is refused before it is downloaded. This used to be the limit on the XML of a list that is opened (Max filelist size, Settings > Advanced > Experts only), which the same tab now shows as well (iceman50)
* Combo boxes sized to their contents no longer cut off their longest entry: they now leave room for the drop-down button as Windows draws it (iceman50)
* Leave files out of the share by extension however the extension is written: "nfo", ".nfo" and "*.nfo" all work, in any letter case (Settings > Sharing > Filtering). "*.nfo" and spaces after a semicolon left the files shared, upper-case names such as README.NFO were shared despite the filter, and "nfo" also left out names merely ending in those letters, such as readme.info. A change made while the share is being refreshed now applies as soon as that refresh finishes instead of being dropped (iceman50)
* Draw the items Windows adds to a menu, such as the shell menu of a file list or a finished download, in the colors of a dark theme: they had a white border, white separators, a light icon column and gray text (iceman50)
* Show the word "Theme" beside the toolbar's theme list on the toolbar's own background in the Windows light look, instead of on a gray block (iceman50)
* Lock DC++ with a password: set one on the Other tab of the Experimental window (View > Experimental), then type /lock in any chat, or have DC++ lock when it is minimized or when it starts. While locked, the window shows only a password box; keyboard shortcuts, the tray menu, taskbar previews and the window title reveal nothing, balloon pop-ups hide the message, and links opened meanwhile wait until it is unlocked, while hubs and transfers keep running. DC++ can also ask for the password before exiting. Only a salted PBKDF2 hash of the password is stored (iceman50)
* Hash files on different drives or network shares at the same time, as AirDC++ does: each drive is still read one file at a time, so a hard disk or a NAS is never made to seek between files. Two shares on a network drive hash about 1.7 times as fast. New option "Drives hashed at the same time" on the Transfers and hashing tab of the Experimental window (default 2; 1 hashes one file at a time as before); "Maximum hash speed" now applies to each drive (iceman50)
* Let searches, uploads, file lists and hub info updates use the share at the same time instead of one after another: a search through a large share (about 0.1 s for a million files) held up every upload request meanwhile, which now waits microseconds. Hash results, refreshes and finished downloads still change the share one at a time (iceman50)
* Share folders given as network paths (\\server\share): they could not be added ("Private Send storage cannot be shared") and existing ones shared no files at all, because the check that keeps privately received files out of the share treated every network path as private (iceman50)
* Start in seconds with very large shares on network drives: loading the share cache checked every cached file for privately received files over the network, which took about an hour for a million files on a NAS; the check is now made once per shared folder, loading is about 25 times faster on local disks as well (3.5 s for a million files), and the share cache is now also used for \\server\share folders (iceman50)
* Stop rescanning slow shares without a break: the automatic refresh was timed from the start of the previous one, so a scan that took longer than the interval was followed straight away by the next; it now waits from the end, and at least as long as the last refresh took. A shared folder that can't be reached (a NAS that is off) keeps its contents instead of disappearing from the share, each shared folder is shared as soon as it has been scanned, and closing DC++ no longer waits for a scan to finish (iceman50)
* Serve uploads at full speed while the share is refreshed: every requested file was read in full to check its hash before the first byte was sent, which on a NAS took minutes per large file; the stored hash for the file's size and date is used instead (iceman50)
* Answer searches of large shares hundreds of times faster: the hub search skipped the name filter that rejects most searches, the filter was too small to reject anything in a large share, and matching lowercased every shared name for every search; searches that match nothing now take microseconds (iceman50)
* Keep uploads, searches and hashing going while the file list is generated or the share cache is saved: both held the share lock for the whole job (about 25 s for a million files). A newly hashed file no longer forces a new file list for the next request, file lists for share profiles are cached instead of built twice in memory for every request, and saving the share cache is about seven times faster (iceman50)
* Count the share size and number of files once per change instead of going through every shared file twice for every hub on each info update (iceman50)
* Hash small files up to five times faster with a fifth of the queue memory: .sfv files are read once per folder instead of once per file, small files are read through the already open file, hashing progress no longer goes through the whole queue, and a file whose date changed after it was queued is hashed as it is instead of being skipped. Finished downloads are recorded as hashed (they were verified while they were downloaded) instead of being hashed again (iceman50)
* New option "Report each hashed file in the system log" on the Transfers and hashing tab of the Experimental window, off by default: hashing now reports one summary per folder (iceman50)
* Use about a third less memory per shared file: a file's real path is only stored when it can't be derived from its folders (iceman50)
* A file downloaded over a shared file replaces it in the share instead of the old size and TTH staying listed, and with "Add finished files to share instantly" it is found by TTH searches and appears in the file list right away (iceman50)
* Privately received files can no longer be shared through a junction or symbolic link to the receive folder, or through a path such as \\localhost\C$ that leads to it; the scan checks a received file's marker when the file is hashed instead of opening every shared file on every refresh (iceman50)
* /rebuild no longer loads every hash tree into memory, and waits until a share refresh has finished, as it would otherwise remove the hashes of files not scanned yet (iceman50)
* Keep hashing while shared folders are scanned: every share refresh, including the one after startup and the automatic refresh, paused hashing until the scan finished, so on network drives hashing seemed to stop by itself for long periods (iceman50)
* Draw settings pages completely the first time they are shown: lists such as the shared folders on the Sharing page stayed empty until something made them repaint, and in dark or custom themes the Favorites, Notifications, User commands, Search types and Experimental pages kept a light background until visited a second time (iceman50)
* Scan large shared folders in a fraction of the time: refreshing the share slowed down with the square of the number of files in a folder, so a folder of 40,000 files took about 4.5 minutes and one of 150,000 about an hour (it now takes under 2 seconds for 40,000), and every file cost several extra trips over the network on network drives (iceman50)
* Start from the share cache also when "Don't download files already in share" is enabled. That setting turned the cache off, so every start rescanned all shared folders before the window appeared. Queued files that are already shared are still removed, now once the background refresh has confirmed they really are shared, so a file deleted since the last run no longer removes a valid download (iceman50)
* Search a file list window without freezing it: Find and Find next opened every folder they passed, so a search through a list of 200,000 files took about 13 seconds when the match was far away or there was none, and 6-7 seconds for each Find next. Both now take a fraction of a second and find the same items (iceman50)
* Keep the keyboard focus where it was when a help popup opens in a dark or custom theme: the popup took the focus, showed a text cursor in the help text and made the settings window flash as it lost activation (iceman50)
* Stop the whole window from flickering when a tooltip or help popup appears: creating one was mistaken for a Windows theme change, which redrew every control in the application (iceman50)
* Show the help popups (F1 and the settings window's help tooltips) in the colors and border of a dark or custom theme instead of yellow with a light 3D border; light themes keep the Windows tooltip colors (iceman50)
* Share files dropped into a private chat with that user only. They were available to everyone on the hub for the rest of the session: anyone could find them by searching for their name and download them. They no longer appear in search results, and only the person you sent them to can download them (iceman50)
* Apply a favorite hub's share profile however the hub's address is written. Opening the same hub as, for example, dchub://hub.example instead of hub.example:411 (from the public hub list or a chat link) showed it the full share. Editing a favorite's address keeps its share profile for a hub window still open on the old address, and changing favorite hubs no longer races with searches and uploads on other threads (iceman50)
* Stop the settings window from repainting nonstop while it is open, which kept a processor core and the graphics card busy. It happened on the Favorites, Sharing, Notifications, User commands, Search types and Experimental pages in every theme, and with dark or custom themes also on Personal information, Appearance, Themes, Tabs and Windows (iceman50)
