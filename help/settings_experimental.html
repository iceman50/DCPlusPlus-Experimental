Experimental

The Experimental window holds the theme, the icon and emoticon packages and every option that DC++ Experimental adds to DC++; the Settings dialog keeps the options of DC++ itself. Open the window from View > Experimental, or with the button on the Experimental page of Settings (which closes Settings as OK does). Its tabs are Themes, Icons, Emoticons, Chat and sharing, Transfers and hashing, Private Send, Protocol limits and Other. Each tab lays its groups out in two columns when the window is wide enough, and in one otherwise; the box at the bottom shows the help for the option with the focus.

Changes apply at once, without an OK button: check boxes and lists when they change, and number and text fields after a short pause in typing, when Enter is pressed or when the field is left. A number field keeps its value within the allowed range, and text that isn't a number is replaced by the current value when the field is left. Settings are saved automatically shortly after a change.

Themes

The Themes tab edits the light or dark mode, the theme presets and the fonts and colors of the interface, lists, chat and user matching definitions, with a live chat preview. See Themes.

Icons

Icon packages
The icons DC++ uses in its menus, toolbar, tabs and lists. Select a package to preview each of its icons on a light and on a dark background, at the size chosen above the preview; point at an icon to see its name. Use this package (or a double click) switches to it. Windows that are already open keep their icons until DC++ restarts. Automatic uses Dark.dcico for the dark appearance and the icons built into DC++ otherwise; Embedded icons always uses the built-in ones. Packages are .dcico ZIP files containing info.xml and multi-resolution ICO files, found in the IconPacks folder (Open folder); Browse picks one from elsewhere, and Reload lists the folder again. An icon a package doesn't have is shown from the built-in set.

Emoticons

Emoticons
Turns emoticons in chat on or off and chooses the emoticon package (.dcemo), its display size and the preferred bit depth of its images. The preview on the right shows what the selected package contains. Browse picks a package from elsewhere, Build makes one from images, and Import XML converts an older XML emoticon package. Choose Custom / edit selected in the package list to add, update or remove emoticons.

Package extraction limits

Emoticon packages (.dcemo) are ZIP archives that are extracted when a package is selected or previewed. These limits stop a crafted package from filling the disk; extraction stops with an error as soon as one is exceeded, counting the data actually decompressed.

Maximum package entries
Maximum number of entries (files and folders) in a package. Minimum: 1. Maximum: 65535. Default: 4096.
Maximum extracted file size
Maximum decompressed size of any single file in a package, in KiB. Minimum: 1 KiB. Default: 16384 KiB (16 MiB).
Maximum total extracted size
Maximum decompressed size of all files in a package together, in KiB. Minimum: 1 KiB. Default: 131072 KiB (128 MiB).

Chat and sharing: rich text and temporary shares

Enable ADC RTF0 CommonMark chat
Advertise ADC RTF0 support on hubs and direct CCPM connections and render its safe CommonMark dialect. Supporting chats provide the RTF0 editor and drag-and-drop attachments.
Enable temporary file sharing in chats
Allow unshared files dropped on any connected ADC or NMDC hub or private chat—and files selected by the RTF0 editor—to be hashed and exposed by exact TTH for that route. Plain and RTF0 chat displays keep the magnet URI visible and clickable and show its human-readable file size; RTF0 routes may additionally render formatted attachments and inline images. Disabling this prevents new temporary shares and makes existing temporary entries unavailable to search or transfer while retaining them in the management list until removed or the application exits.
Insert dropped image files as inline media
Use RTF0 inline-image syntax for recognized BMP, GIF, ICO, JPEG, PNG, TIFF, and WebP files when the chat supports RTF0. Plain ADC and NMDC chats always receive an ordinary magnet link.
Rich text message size limit
Maximum UTF-8 size of an incoming or outgoing ADC RTF0 rich text message, in KiB. Larger incoming messages are replaced with an omission notice; larger editor drafts cannot be inserted into chat. Minimum: 1 KiB. Default: 64 KiB.
Clickable chat link length limit
Maximum URL or magnet URI length that will be turned into a clickable chat link. Longer links remain visible as plain text. Minimum: 1 character. Default: 256 characters.
Maximum temporary shares
Maximum number of temporary RTF0 attachments retained for the current application session. Adding another entry removes the least recently used entries first. Minimum: 1. Default: 256.
Automatically remove temporary shares after
Set the lifetime in minutes, measured from the most recent addition of the file to a chat draft. Default: 0 (no automatic expiration). Changes apply to existing entries too. Expiration stops new searches and downloads through the temporary share; it does not delete the local file, remove posted messages, or affect normally shared files. Expired entries are cleaned up every minute.
Active temporary shares
Lists the session-only files currently addressable by exact TTH, including their route and local path. These files appear in search results only on the hub or CCPM route where they were added, remain absent from file lists and share totals, and can be downloaded by TTH only from that route. Remove selected entries, clear the full list, or refresh file availability from here.

Transfers and hashing: file lists

Largest file list to download
Largest full file list downloaded from another user, in MiB, as the user announces it: the compressed size of a .bz2 list, or the XML size of an uncompressed one. A larger list is refused before anything is written to disk. A list larger than the largest file list to open is refused as well, since it could not be opened. 0 means no limit. Default: 512 MiB.
Largest file list to open (XML)
The most XML a file list may contain when it is opened, in MiB; it protects against lists that need a great deal of memory to decode. This is the Max filelist size of Settings > Advanced > Experts only, shown here too. 0 means no limit. Default: 512 MiB.
Generated partial file list limit
Maximum uncompressed XML size generated in response to a partial file-list request, in KiB. Minimum: 1 KiB. Default: 65536 KiB.
Received partial file list limit
Largest partial file list accepted from another user, in KiB of uncompressed XML. Partial lists are kept in memory while they download, and compressed transfers can expand a small amount of data into a very large list, so larger lists are refused before they are received. A recursive list over the limit is downloaded as a full file list instead, which is saved to disk. Minimum: 1 KiB. Default: 393216 KiB (384 MiB).
Prefer Zstandard over zlib when the peer supports both
Use Zstandard for downloads from clients supporting the experimental ZST1 extension on ADC or NMDC. Older clients continue to use the existing compression. Full lists from supporting clients use compressed XML instead of bzip2. Requires Compress transfers. The default is off. The preference affects new download requests; supporting peers may still request Zstandard uploads.
Cache file lists on disk and load file entries on demand
Build a compressed disk index when opening XML, bzip2, or Zstandard lists. Directory metadata remains available, while file entries load when a directory is visited and are released when leaving it. The original list is retained. The first open builds the index; later opens reuse it unless the source changes. Search, queue matching, ADL rules, and directory downloads include unloaded entries. One very large directory still needs memory for its own entries. This uses additional disk space and defaults to off. Applies to newly opened lists.

Transfers and hashing: multi-connection transfers (MCN)

Maximum regular download connections per user
Limits simultaneous regular ADC MCN1 download connections opened to one user. The peer's CO limit is also respected; a missing CO field or CO0 means that the peer has no separate per-user limit. Multiple connections can download different files, and may also download different segments when segmented downloading is enabled.
Maximum regular upload connections per user
Limits simultaneous regular ADC MCN1 upload connections accepted from one user. This value is advertised to MCN1-capable peers. Upload slots count unique regular upload users rather than their physical MCN connections, and excess connections are redistributed when another user needs a slot.
Priority connection
MCN1 automatically maintains one additional connection for partial file lists and files smaller than 64 KiB. It is outside both regular per-user connection limits and the normal upload/download slot totals. Its transfer role is fixed for the life of the connection; full file lists, file trees, and larger files remain on regular connections.

Transfers and hashing: hashing and share database

Maximum hash speed
Limits file hashing speed in MiB/s, for each drive being hashed. Zero means unlimited.
Drives hashed at the same time
Files on different drives, or on different network shares, are hashed at the same time, up to this many at once. Each drive is still read one file at a time, so a hard disk or a NAS is never made to seek between files; this is how AirDC++ hashes. When more drives are waiting than this allows, they share the hashers. Use 1 to hash one file at a time across all drives. Default: 2 drives. Minimum: 1. Maximum: 16.
Hashing worker threads
Maximum number of CPU workers used to calculate independent Tiger Tree Hash blocks for one file. File input remains sequential and SFV checks remain ordered. DC++ may use fewer workers when the file has too few blocks, the computer exposes fewer logical processors, or the fixed 256 MiB pipeline-memory limit would be exceeded. Use one thread to retain serial hashing. Default: 2 threads. Minimum: 1. Maximum: 64.
Hash database write batch size
Number of SQLite hash database row changes grouped into one transaction. Larger values improve bulk hashing throughput; smaller values commit newly hashed files sooner.
Report each hashed file in the system log
Adds a line to the system log for every file that is hashed. When this is off (the default), hashing reports one summary per folder instead, which keeps the system log readable while a large share is hashed.
Verify hash database on startup
Runs a quick SQLite integrity check when the hash database opens.
Compact hash database after rebuild
Compacts SQLite storage after a hash database rebuild.
Use cached share tree on startup
Loads a validated cached share tree before the background filesystem refresh completes, for local, mapped and network (\\server\share) folders alike. Loading it reads no shared file, so it is quick even for very large shares on network drives.
Verify / Full check / Optimize / Compact
Runs hash database maintenance immediately. Verify uses SQLite quick_check, Full check uses integrity_check, Optimize updates query planning hints, and Compact checkpoints the WAL and reclaims unused space.

Private Send (experimental PFT1)

Disabled by default. Private Send offers a selected file directly from private chat without a search result, file list, or public magnet. Both clients must support the same experimental draft, use an ADCS hub and a fresh TLS 1.2+ direct chat (TLS 1.2 requires ECDHE and authenticated encryption). Manual contact verification is temporarily off by default for testing. After enabling, reconnect an existing direct chat to negotiate support. Open Private Send... from the chat menu, or click the file icon in the PM status bar. This shortcut is also available before the connection or contact verification is ready.

Clear list dismisses finished, cancelled, declined, expired and failed transfers for this contact. Active and paused transfers stay in the list, and saved files are kept.

Require contact verification (off for testing)
Default: off. When enabled, each person chooses Add contact to verify the actual peer certificate against the identity advertised by the current secure hub and remember it. Alternatively, use Details > Compare fingerprint... to compare a CID and fingerprint received independently. Turning verification on cancels transfers without an approved matching fingerprint. Testing mode skips contact approval; it does not automatically save contacts as verified.
Offer expires after
Lifetime of a new outgoing offer before acceptance. Default: 15 minutes. Range: 1–1440 minutes.
Accepted transfer expires after
Maximum lifetime after acceptance. Default: 1440 minutes. Range: 1–10080 minutes. The earlier peer deadline wins. Existing deadlines are never extended by settings changes.

Recipients explicitly accept each file. Received files undergo full hash verification and Windows attachment policy before being saved below PrivateSend\Received in the profile's local data directory. They are never opened or shared automatically. Pause permits recipient-initiated resume for up to 30 minutes within the hard deadline, with at most three attempts. Disabling the feature or forgetting a verified contact revokes transfers.

Expiry removes access and incomplete received files; it never deletes the sender's original or a completed received file. Sessions do not survive restart. PFT1 is a proposed identifier, and stable interoperability and independent security review remain release gates.

Protocol limits: direct private-message channels (CCPM)

These controls govern automatic recovery of an encrypted direct private-message channel. Each failed attempt uses an exponentially longer delay, with random jitter to keep two identical clients from retrying in lockstep.

Initial automatic reconnect delay
Delay before the first automatic reconnect and the starting point for exponential backoff. Minimum: 1 second. Maximum: 3600 seconds. Default: 5 seconds.
Maximum automatic reconnect delay
Upper bound for the exponential reconnect delay. A value below the initial delay is raised to match it. Minimum: 1 second. Maximum: 3600 seconds. Default: 60 seconds.
Stable connection reset time
Time a direct channel must remain connected before a later disconnect resets the accumulated automatic-attempt count. Minimum: 1 second. Maximum: 86400 seconds. Default: 60 seconds.
Maximum automatic reconnect attempts
Number of automatic attempts permitted before reconnection is paused. Starting the direct channel manually resets the attempt budget. Minimum: 1. Maximum: 100. Default: 5.

Protocol limits: hub authentication

Minimum ADC password challenge length
Shortest password challenge (salt), in Base32 characters, that an ADC hub may send before DC++ answers it with your password hash. Short challenges make captured responses easier to crack. If a hub sends a shorter one, the password is not sent, the hub is disconnected and automatic reconnection is turned off. Lower this only for older hub software you trust. Range: 2 to 39 (39 is the 24 bytes the ADC specification requires). Default: 10, as in DC++ 0.884.

Protocol limits: NMDC hubs

Default encoding for NMDC hubs
Character encoding (code page) used for NMDC hubs that do not have their own encoding in the favorite hub properties. It applies to hub chat, nicks, private messages, search results and direct connections. Windows default uses the system code page. NMDC hubs use a single encoding for everything, so DC++ no longer guesses the encoding from each line: on a hub that uses UTF-8, choose 65001 (UTF-8) here or in that hub's favorite properties, otherwise names and messages with non-English characters will be garbled. Default: Windows default.

Protocol limits: protocol resource limits

These limits protect DC++ from excessive memory, connection, and packet use. The defaults are recommended for normal use. Lower values can reject legitimate traffic; higher values increase resource usage and exposure to denial-of-service traffic. Changes apply to new operations without restarting DC++. The partial file list limits are on the Transfers and hashing tab.

Queued protocol data limit
Maximum unsent protocol data retained for one socket, in KiB. The socket is disconnected when another write would exceed the limit. Minimum: 1 KiB. Default: 16384 KiB.
Concurrent peer connection limit
New incoming peer connections are rejected when this many incoming and outgoing transfer or private-message connections already exist. Hub connections are not included. Minimum: 1. Default: 512.
Incoming connection flood window
Time span used to count incoming peer connection attempts from each IP address. The allowed burst is derived from the multi-connection upload setting. Minimum: 1 millisecond. Default: 10000 milliseconds.
Global UDP rate window
Time span used by the global incoming search-result UDP packet limiter. Minimum: 1 millisecond. Default: 1000 milliseconds.
Global UDP packet limit
Maximum incoming search-result UDP packets processed during the global UDP rate window. Minimum: 1. Default: 2000.
Per-peer UDP packet limit
Maximum incoming search-result UDP packets processed from one IP address during the per-peer UDP rate window. Minimum: 1. Default: 500.
Per-peer UDP rate window
Time span used to count incoming search-result UDP packets separately for each IP address. Minimum: 1 millisecond. Default: 10000 milliseconds.
Tracked UDP peer limit
Maximum number of IP addresses retained by the per-peer UDP limiter. New addresses are ignored while the table is full and no expired entries can be removed. Minimum: 1. Default: 4096.
Encrypted UDP packet limit
Maximum encrypted search-result UDP packet accepted for decryption. Valid packets must also be at least 32 bytes and aligned to a 16-byte AES block. Minimum: 32 bytes. Default: 4096 bytes.
Stored encrypted UDP key limit
Maximum recent search encryption keys retained for decrypting SUDP results. Oldest keys are discarded first. Minimum: 1. Default: 64.
BBS boards per hub limit
Maximum BBS0 boards kept for each hub. Additional boards announced by the hub, or referenced by its posts, are ignored and a single status message is shown. Range: 1 to 1000. Default: 100.

Other: offline message outbox

Keep messages for offline users and send them later
Private messages written to a user who is offline are kept in the message outbox and sent when the user is next online. The same switch is in View > Message outbox, which lists the waiting messages. The limits below apply to new messages and retries; existing messages keep their deadlines.
Maximum retained messages, Maximum message size, Pending messages expire after
How many messages the outbox keeps (1 to 10000), how long each may be (1 to 64 KiB), and how many days a message waits before it expires.

Other: hub user lists

Default user icon size
The global size for hub user-list icons: 16, 20, 24, 28, 32, 40 or 48 pixels, scaled for display DPI. The default is 16. Each favorite hub can override this in Favorite Hub Properties or the Icons dropdown beside its user filter. Choosing Default removes the hub override and inherits the global or favorite-group setting. Changing the global default updates open hubs that inherit it. Non-favorite hubs keep a selected size only for the current window; adding the hub to Favorites saves that choice.

Other: System Log

Maximum System Log items
Maximum number of recent messages retained for the System Log window and available when it is opened or restyled. Lowering the value discards the oldest retained messages. The visible RichEdit buffer also retains its independent 96 KiB safety limit. Minimum: 1 message. Maximum: 1000 messages. Default: 100 messages.

Other: country database

Download URL
An HTTPS download URL for a Country .mmdb file or a standard .tar.gz archive. Public GitHub release assets are supported and require no login. Updates run once daily while DC++ is running; failed attempts retry after six hours. Use File > GeoIP database update to start immediately. Progress and cancellation are available in the transfer view. Failed updates preserve the working database. One database covers IPv4 and IPv6, and lookups are local. Guessing user countries and their format are in Settings > Appearance.

Enable Download directly from MaxMind (testing override) to use your numeric MaxMind account ID and full license key instead of the download URL. The key is encrypted for your Windows account. Turning off the override restores the download URL. Existing testing configurations with saved keys retain direct MaxMind downloads automatically. Changing these options starts an update; File > GeoIP database update starts one at any time.

Other: password lock

The password lock hides DC++ behind a password while you are away from the computer. When DC++ is locked, its window shows only a password box: the menu, the toolbar, the open tabs, the transfers and the status bar are hidden, keyboard shortcuts do nothing, the taskbar shows no tab previews, the window title doesn't name the hub or user in view, and balloon pop-ups say what happened without showing the message. Hubs, searches, uploads, downloads and hashing keep running as usual. Enter the password and press Enter, or click Unlock, to use DC++ again. Links, magnets and balloons you click while it is locked open once it is unlocked.

Type /lock in any chat window to lock DC++ straight away.

The lock keeps other people at your keyboard out of DC++. It doesn't encrypt anything: your settings, logs and downloads stay readable to anyone who can use your Windows account, so lock Windows itself (Windows key + L) for real protection. If you forget the password, close DC++ and remove the LockPassword line from DCPlusPlus.xml in your settings folder; DC++ then starts without a lock password.

Set password, Change password, Remove password
Sets the lock password, which the options below need. Changing or removing it asks for the current password first. DC++ stores only a salted PBKDF2-SHA256 hash of the password, never the password itself. The change takes effect at once; removing the password also turns the options below off.
Lock DC++ when it is minimized
Locks DC++ whenever its window is minimized, to the taskbar or to the tray.
Lock DC++ when it starts
Starts DC++ locked. Hubs you were connected to reconnect as usual behind the lock.
Ask for the lock password before exiting
Asks for the lock password whenever DC++ is closed, from the window, the tray or the taskbar, so nobody else can stop it. This applies whether or not DC++ is locked. Shutting down or signing out of Windows is never held up.
